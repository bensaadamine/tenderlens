# TenderLens — decisions

The code cites these by number ("decision 15"). Each is settled and measured; the numbers never change. Measurements behind them are summarised in the component pages (`docs/agents/`).

## Scope and output
1. The audience is the state auditor.
2. After the award only. Bids are confidential and not in our data.
3. Never output "fraud". Output: the competition does not appear genuine, for these reasons, at these locations. Every finding has a source line; a person decides.
4. Market concentration (M3) is context, not evidence.
5. No signal is absolute — each is measured against its own group.
6. Scope: the top 20 UNSPSC-4 goods categories (`reports/selected_unspsc4.json`).
7. Ground truth: synthetic rigged tenders measure recall; real complaints and cancellations prove relevance (not collected yet).
8. The headline metric is precision@50.

10. The specification is in the solicitation body, in a named section (usually `ANNEX A`).
11. Rules find candidates; the M2 agent judges — except where a thing sits (25) and the exact text clearances (44).

## Level 2 — numbers against peer tenders

13. Peers are grouped by UNSPSC-8; level 2 stays silent for an attribute until it has 8 peers. Never widen the group for one finding.
14. Store observations, never statistics: medians and spreads are computed on read.
15. Units: convert or drop, never guess. Resolving from context is not guessing (24).
16. Track token usage (`reports/llm_usage.csv`); cache hits are logged at zero.
18. In a unit pattern, compound units come before their prefixes (`km/h` before `km`).
19. A bare dimension word (`length`) is never a canonical attribute name.
20. Two labels with different values in the same tender can never be merged.
21. Tender folders hold only buyer documents. Extraction is scoped by section, never by filename.
22. One observation per tender per attribute per value; in peer statistics a tender counts once (its median).
23. Parse numbers properly, never `replace(",", ".")`: three digits after a comma are thousands.
24. Every observation carries its section and ±3 lines of context, used to resolve ambiguity.
25. Where a requirement sits is decided by rule, not prompt: packaging, shipping, warranty sections are dropped.
26. Peer comparison finds nothing usable today; level 2 ships as the within-document test, low confidence.

## Routing and scoring
27. Only a verified brand finding can raise an alert: one brand → watch; two, or one that is the winner → alert, from document findings alone. What the buyer declared (advance award notice, limited tendering) only ranks a case. "No trade agreement" is context. Context ranks a case but never lifts it to watch, and in selective tendering (only suppliers already qualified may bid) a short window is normal and does not count (2026-11-24). M3 and level 2 add to a case, never make one. A claim scores only if its words were checked against its source. The weights are orderings, not probabilities.
28. M1 (rules) never decides whether a tender is read: every tender with documents goes to M2. A buyer's single-supplier justification is not checked by an agent.
29. Brand names are looked for in the requirements section only (whole document when none is found); the model code must follow the name; a measurement ("610MM", "350W") is not a model code; a maker the sentence names needs no model code ("manufactured by X", "approved distributor of X", "genuine X", 2026-11-25); bidders' questions are skipped; in an amendment only change clauses, answers and restated requirements are read. "Or equivalent" and the Equivalent Products clause (its text, or its number B3000T alone) are checked against the whole text. So is the buyer accepting other products in other words ("equivalent … will be accepted", "products that meet the same technical specifications"), outside bidders' questions; the defence definition "Substitutes and alternatives … will be considered" is still not a clearance (2026-11-24). An operating system or browser is the buyer's environment, never a finding. A list the buyer introduces as approved or acceptable products ("as follows: (a) … (f)", markers (a) a) (i) 1. or bullets), whose items name a product (a model code or ™/®) of two or more makes, is a list of makes: the bidder may supply any one. It is a text clearance, not re-checked by the agent, unlike a list of vehicle makes recognised by its shape (2026-11-25; the 4111 blood-alcohol kits). A hit's line is found from its position in the document's text.


## How the system runs
31. Tender by tender against a growing knowledge base, in publication order: close → base (a peer for later tenders); alert or watch → quarantine (never a peer). The auditor's `clean` returns a tender to the base; `confirmed` keeps it out as a real test case. Each case is logged before its register line (crash-safe). A base is started once (`run --install`, 2026-11-24): the oldest 70% of the tenders to process, by publication date, rules only (0 tokens). The newest 30% and every later tender are new tenders, read with the agents.
32. The agents (M2, M3) each have a goal, tools the model chooses, a loop with a step budget and a trace — one shared loop (`agents/agent_loop.py`). Safety rules stay in code. With no model answering, a run stops and the next run resumes there.
33. Which tenders are processed (2026-11-21, user decision): only a tender **awarded** (a matching row in the award file) **with documents** goes through M1–M4 and can reach the queue. A cheap gate decides it first, from the notice, the award file and the list of extracted files, before any text is read (`one_tender.gate`; the award lookup is M3's own, `m3_investigator.find_award`). The others are only recorded: cancelled, RFI or supply arrangement → "not an audit case"; open → re-checked on every run; no documents → re-checked when documents appear; closed with documents but no award found → the family's "Award not found" list, for the inspector to check by hand (sorted by date, or with the brand names the level-1 rules find required first; no model), re-checked on every run and processed as soon as its award appears. Several award rows: the newest is the award, every supplier listed. A match by solicitation number counts only if the award's title shares a meaningful word with the tender's (2026-11-24): buyers reuse their numbers — 12 of 404 tenders in 2510/4110 had been matched to another purchase's award. An advance contract award notice is not an audit case (user decision 2026-11-24): the supplier was announced in advance and other suppliers could object, so once it is awarded there is nothing for the auditor to add.
34. One pinned model: Groq gpt-oss-120b answers every call of agents 1–3 (the rules assistant runs on a local model instead, 53), through one or two Groq keys (`GROQ_API_KEY2`, a second account: same model, its own rate and daily quota; each call goes to the key that can take it soonest). Every agent result says which model answered. A second provider (Gemini, shared calls with `TENDERLENS_SHARE=1`) was removed on 2026-11-26: never used, and two models give different verdicts.
35. Interface: one command with subcommands, and a local page for the auditor (`python tenderlens.py serve`, FastAPI, built 2026-11-12, redesigned 2026-11-25). A top bar leads to four places: **To decide** (every flagged case of every family and every split purchase waiting for a verdict, in one list, most serious first), **Families** (one row per family, its base, its awards not found, the trash), **Rules** (the rules of law and the rules assistant) and **How it works** (the four agents, agent activity, the synthetic test). A case shows the tender's own words marked as evidence, the rule each reason rests on, who settled each name, and the verdict (clean / confirmed). Commands run with the agents (user decision 2026-11-26: no mode switch on the page). When no model answers (the quota is spent), the command's page offers to continue with the rules only; the replay from the cache stays on the command line (`--offline`) for the demo and the tests. The page has no re-run button: a tender is not read twice by hand; it can be moved to the trash instead (decision 54). Rules vs agents is `python tenderlens.py demo`, its result kept in `deliverables/results/rules_vs_agents.txt`.
36. Share package (deprioritised): one zip of caches, knowledge bases and labels.
37. Evaluation reports a tuning set (cases rules or prompts were fixed on — flattered) and a held-out set (never used for tuning — the score to quote). Every run writes its own dated folder; never overwrite. A third set, `sample` (2026-11-24): 102 tenders drawn at random, 17 in each of 6 families; every name the rules raise is labelled, plus the lock-ins found by reading the requirement lines (`tests/m2_sample.csv`).
38. M3 agent: "same company" needs a postal code shared with the winner itself (no chains); a decision applies to the whole group of spellings.
39. M4's checks run in a fixed order on cases with a brand finding: the M3 agent checks the winner's spellings, the winner's other award titles are shown. A model choosing the checks was measured worse (2 false alarms vs 0) and was removed (2026-11-24). The first check, the M2 agent re-reading each finding, was removed (user decision 2026-11-26): the system always runs with the M2 agent, which already letters every finding, so the re-read had nothing to do (it mattered only with M2 on rules alone, where it removed 7 of 7 false alarms).
40. M2 agent, the supply test: "f" only if the bidder must supply that brand's product; if the purchase must connect to it, be controlled by it or be based on it, it is "c". Before its first step the agent is shown what the tender buys and every sentence about equipment the buyer already has.
41. A hybrid multi-agent workflow: agents where judgement is needed (M2, M3), rules where exactness matters (M1, scoring, routing, quote checks), each choice measured. No model call is added just to make a component an agent.
42. Level 2 is kept, dormant, behind one switch (`--no-level2` skips its extraction and comparison).
43. The demo: seven chosen tenders, two setups side by side (rules only, every agent), replayable offline.
44. Who settled each brand name is recorded (`decided_by`): a rule, Wikidata, or the M2 agent. Rules keep the exact text clearances. One brand written several ways is one finding: a spelling joins a shorter finding whose words it begins with.
45. One command (`python tenderlens.py`), normal packages; what M2 and M3 hand to M4 is defined once (`agents/evidence.py`).
46. An offline replay never calls a provider: a missing answer is reported, and no key is needed.
47. One run's choices are one object (`pipeline/settings.py`), passed down as parameters; settled switches are removed.
48. Brand = winner needs every word of the brand, any length, in the winner's name (or an accepted spelling): a shared word is not identity ("General Electric" is not "General Motors", "GE Healthcare" is not "Siemens Healthcare").
49. Names are read one way (`tools/names.py`: words, any length, case and punctuation ignored), and each comparison states its own rule: merging spellings (a spelling begins with a shorter finding's words), M2's quote check (an "f" quote holds the whole name, word after word), brand = winner (48). No fuzzy matching.
50. The synthetic test (`eval synth`) runs M2 once per copy and reads each brand's outcome from that run; it reports its false-alarm guards apart (D: brand with "or equivalent", E: brand only in a bidder's question, F: untouched copy, judged on its route); its ranking is "rigged copies in the top 50", never called precision; each run keeps its own folder with settings and fingerprints. Whether a base already accepts equivalents can be decided by hand (`--review`) instead of by the detector's own patterns. The verdicts are kept when `--review` is run again. Rebuilt 2026-11-24 over six families (7 bases per family where available, brands of each family's own market); the first set (40 bases of 2510) stays in `reports/synth/2510/`.
51. Limited tendering is one declared signal, its method only (user decision 2026-11-25). The red flag would be limited tendering without a justification, but limited tendering never carries a filed reason in the data (0 of 232); reasons appear only on advance award notices (not audit cases, 33) and, as noise, on 189 competitive notices. So the reason field is not read; `limited_tendering_method` ranks a case and never queues it (27).
52. Split purchases (agent 3, 2026-11-25): a goods contract may be given without bids only if it is $25,000 or less (Government Contracts Regulations s. 6(b)(i)). Rules find the groups from the award file alone (no documents): same buyer and supplier, non-competitive goods awards of $25,000 or less each, within 30 days of the first, together over $25,000 (15 groups in all goods). The agent judges each group split / separate / unclear with tools on the award file (history, habit, detail); a "split" needs a quote found in two or more of the group's own titles or descriptions and in fewer than 1 in 10 of the same buyer and supplier's other contracts (2026-11-25: "Office Seating", 29% of the pair's contracts, had passed); a split never backed by such a quote ends as unclear; it routes to watch, never alert. The labels (`tests/split_labels.csv`) were written blind by a separate agent that saw only the groups. Rules alone: 10/15 as labelled, 3 false splits. Agent, first run: 9/12 decided as labelled, 2 false splits, 3 without verdict (the quote check refused splits it could not back).
53. The rules of law behind each signal are shown to the auditor (2026-11-25): `tools/laws.py` lists them with their official source and a short quote (Government Contracts Regulations s. 5 and 6; Canadian Free Trade Agreement art. 503, 504, 509, 511, 513; Supply Manual 3.15.5; the B3000T clause), and every reason of a case links to its rule. The **rules assistant** (`agents/rules_agent.py`) answers questions from the official texts (`prepare laws`, Windows) on a **local model** (Gemma 4B through Ollama, user decision 2026-11-25: no quota, nothing leaves the computer). A 4B model is unreliable in a free tool loop, so the code drives three steps: the model plans search words, the code searches hybrid (keywords by BM25 and meaning by local embeddings, fused by Reciprocal Rank Fusion; user decision; measured on 15 questions: hit@6 keywords 8, meaning 14, hybrid 13; keywords only without the embedding model), the model answers from the passages; every quote must appear word for word in a passage shown (one retry, told why); without a model, the passages are shown. It explains the texts; it never gives legal advice.
54. The trash (user decision 2026-11-26): the auditor can take a tender out of a family. It is one line appended to the register (pile `trash`), so it can be undone: the tender's requirements leave the base at once (level 2 reads the base only), it leaves the queues, verdicts and re-runs refuse it, and runs skip it. **Restore** appends the line it had before. **Delete forever** (only from the trash) is the one rewrite of the knowledge base: the tender's lines are erased from `observations.csv`, `cases.jsonl`, `register.csv`, `feedback.csv`, `award_not_found.jsonl` and the batch queues, each file written to a copy and swapped in whole; one `deleted` line stays so the next run does not read the tender again. The award history (agents 2 and 3) is public data and is not touched. Tested in `tests/test_trash.py`.
